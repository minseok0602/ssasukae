# 가창자 백엔드 연결 중단과 공연 재개

브랜치: `codex/performer-connection-recovery`

## 동작

- 관전자는 백엔드 연결만 끊겨도 미디어 수신을 유지한다. 재접속 시 WebSocket 구독 후 최신 방 스냅샷을 반영한다.
- 가창자는 WebSocket 종료/STOMP 오류 시 실제 MR 위치를 먼저 읽고 MR·마이크·채점 진행을 일시 정지한다. 같은 단절의 재시도는 첫 정지 위치·시각·식별자를 유지한다.
- 정지 기록은 메모리와 해당 탭의 sessionStorage에 보관한다. 인증 토큰이나 녹음 데이터는 넣지 않는다.
- 일반전·수성전 서버는 STOMP 연결도 별도로 감지해 `SUSPENDED`를 전파한다. 기존 OpenVidu 미디어 접속 상태는 유지한다. 저지연 모드는 기존 STOMP 프레즌스 경로를 사용한다.
- 재연결된 가창자는 `POST /api/rooms/{roomId}/performances/{performanceId}/connection-recovery`로 정지 정보를 확인받은 뒤 최신 스냅샷을 조회한다. 응답은 204다. 확인 전 들어오는 과거 PLAYING 스냅샷이나 재개 이벤트로 MR을 실행하지 않는다.
- 서버는 현재 공연 ID, 소유 가창자, 정지 위치·시각과 재접속 유예를 검사한다. 종료·교체된 공연의 요청으로 현재 공연을 변경하지 않는다. 동일 단절 식별자의 재전송은 이미 재개된 공연을 다시 정지시키지 않는다.
- 공연 스냅샷과 재접속 마감의 등록/삭제를 Redis Lua의 조건부 변경으로 묶는다. 기존 스냅샷 JSON은 추가 필드 없이도 읽고 비교 갱신할 수 있다.
- 기본 재접속 유예 15초가 지나면 취소한다. 유예 안에 연결이 돌아오면 만료 예약을 해제하고, 음원·미디어 준비와 사용자 재개 요청을 기다린다. 준비 중 다시 끊기면 새 유예를 등록한다.
- 재개는 가창자·공연·방 상태를 서버에서 확인한 후 승인한다. 500ms 뒤 공통 재개 시각과 위치를 전파한다. 음원·채점·관전자 가사 시계가 이 기준을 사용한다. 모든 관전자의 ACK를 기다리는 장벽은 두지 않는다.
- 원래 공연 시작 시각은 보존하며 재개 시각과 실제 정지 위치를 새 재생 기준점으로 둔다. 중단 시간이 재생 위치에 포함되지 않는다.
- 같은 공연의 오래된 중지/재개 이벤트와 이전 소켓의 늦은 종료 이벤트가 최신 연결 상태를 되돌리지 않도록 검사한다.

## API 요청

```json
{
  "interruptionId": "브라우저에서 생성한 단절 UUID",
  "interruptedAt": "2026-11-23T00:00:10Z",
  "playbackPositionMs": 22000
}
```

`interruptedAt`은 마지막 스냅샷의 서버 시각으로 보정한다. 위치는 가창자 오디오 엔진의 실제 MR 시간축을 사용한다. 서버는 인증된 가창자에게만 현재 공연 변경을 허용한다.

## 검증

- 운영 Java 전체를 Java 17과 기존 캐시 의존성으로 컴파일했다.
- 관련 공연·분석·결과 테스트 및 실제 Redis 원자성 테스트 65개가 통과했다. Redis 테스트는 별도 컨테이너로 격리한다.
- HTTP 응답 형식·음수 위치 거부, 중복 복구, 유예 만료, 이전 공연/소켓, 재개 직후 재단절, 분석 만료 배치 경합을 검사한다.
- 프론트는 Node 24에서 `pnpm run test:connection-recovery`로 정지 기록과 실제 stageStore의 복원 경합 12개가 통과했다.
- `pnpm exec tsc --noEmit --incremental false`, 변경 파일 ESLint, `pnpm build`를 실행한다.
- Gradle 사용 시 일반 회귀는 `gradlew.bat unitTest`, Redis 원자성은 테스트 Redis를 띄우고 `PERFORMER_TEST_REDIS_PORT`를 지정한 뒤 `gradlew.bat test --tests '*PerformanceInterruptionRedisIntegrationTest'`로 실행한다.

## 범위

서버가 중단된 동안에는 중지 이벤트를 전파할 수 없다. 가창자는 먼저 로컬에서 정지하고, 연결 복구 후 서버 상태를 조정한다. WebSocket/heartbeat로 단절을 감지할 때까지의 지연은 존재한다.

브라우저 종료/새로고침 전의 누적 녹음·채점 데이터를 영속 복구하지 않는다. Redis 자체 유실과 상태 반영 후 이벤트 발행 전 장애에 대한 보장도 추가하지 않았다.

## 실제 브라우저 장애 실험 (2026-11-23)

운영 서버를 중단하지 않고 로컬에 격리한 통합 환경에서 실행했다. 실제 Chrome 두 컨텍스트가 가창자·관전자로 로그인하고, 일반 모드 방 생성·입장·공연 시작·재개 UI를 사용했다. 프로덕션 Next.js 빌드와 실제 Spring 인증·API·STOMP·OpenVidu 게이트웨이 및 웹훅을 구동했다. MySQL 8.4, Redis 7, OpenVidu 2.32는 별도 Docker 컨테이너다.

미디어 전송은 실제 WebRTC이며 getStats의 수신 바이트 증가로 확인했다. Chrome의 가상 카메라·마이크와 120초 합성 MR을 사용했다. 음원 URL만 테스트용 로컬 파일로 대체했고, 운영 DB·Redis·S3 데이터는 사용하지 않았다. 실제 마이크의 음질·누적 채점 정확도·AI 분석은 이 실험의 검증 대상이 아니다.

단절 주입은 애플리케이션 WebSocket만 닫아 OpenVidu 미디어 연결을 유지하는 방식이다. 재접속은 3초 주기로 시도하며 실험 중에는 선택한 사용자의 새 연결을 차단한다. 브라우저가 허용하는 종료 코드 4001로 클라이언트와 서버 양쪽을 닫고, 서버 SessionDisconnectEvent 수신을 확인했다. 초기 주입은 잘못된 종료 코드 때문에 서버 쪽 연결을 유지했으므로 실패 결과를 제품 결함으로 판단하지 않았다.

백엔드 장애는 이 실험에서 띄운 Java 프로세스만 강제 종료했다. MySQL·Redis·OpenVidu와 브라우저는 유지했고 15초 이상 기다린 다음 동일 설정으로 재시작했다. 서버가 중단된 동안에는 브로드캐스트가 불가능하므로 가창자 로컬 정지와 복구 후 취소를 검사했다.

AWS 배포 환경·로드밸런서·다중 백엔드 인계, 물리 장치, 네트워크 패킷이 응답 없이 사라지는 경우, 수성전·저지연 모드 전체 E2E는 별도 검증이 필요하다.


### 최종 결과

최신 프론트 소스를 다시 `pnpm build`한 뒤 2026-11-23 12:32~12:33 KST에 실행한 결과다.

| 검증 | 결과 | 확인 근거 |
| --- | --- | --- |
| 실제 브라우저 입장·미디어 연결 | 통과 | 두 사용자 CONNECTED, WebRTC 연결 및 송수신 바이트 확인 |
| 관전자 애플리케이션 연결 단절 | 통과 | 공연 PLAYING·가창자 MR 유지, 단절 중 미디어 수신 지속, WebSocket 재접속 |
| 가창자 단절·유예 내 복귀·사용자 재개 | 통과 | 로컬 MR 정지, 서버 SUSPENDED, 관전자 정지 이벤트, 정지 위치 조정 후 동일 위치에서 재개 |
| 가창자 15초 유예 만료 | 통과 | 공연 취소·방 PREPARING 복구, 늦게 돌아와도 자동 재생 없음 |
| 백엔드 강제 종료 후 재기동 | 통과 | 로컬 정지, Redis 상태 유지, 복귀 후 만료 공연 취소 이벤트 수신·자동 재생 없음 |

최종 실행에서 관전자 단절 중 수신량은 437,975바이트였다. 가창자 MR의 실제 정지 위치와 재개 시작 offset은 모두 11,389ms였다. 백엔드 종료부터 복구 확인까지는 38.469초로 유예를 넘겼다. 위치 일치는 오디오 소스의 시작 offset 기준이며, 모든 단말의 실제 출력 지연이 0이라는 의미는 아니다.

구조화한 결과는 [실험 결과 JSON](experiments/performer-connection-recovery-results.json)에 보관한다. 로컬 상세 로그·스크린샷·실행 스크립트는 Git에서 제외되는 `backend/ssasukae/build/browser-e2e/`의 `browser-traces.json`, `browser-test.mjs`, `singer-paused.png`, `viewer-paused.png`에 남아 있다. 실험을 위해 생성한 호스트 프로세스와 세 Docker 컨테이너만 종료·제거하며, 결과 파일은 유지한다.
